## 핵심 내용

### 1. 신뢰 곡선 (Agent Trust Curve)
- 에이전트가 추측하고 환각하면서 "원인을 찾았다"고 자신 있게 말하는 일이 반복되면, 사람은 에이전트를 신뢰하지 못하게 됩니다.
- Lauren 은 이 상황을 팀원을 믿지 못하는 매니저에 비유합니다. 신뢰가 없으면 매니저는 마이크로 매니징을 할 수밖에 없고, 에이전트를 다룰 때도 모든 출력을 지켜보느라 병렬화하지 못합니다. 에이전트 하나의 결과도 믿지 못하는데 에이전트 100개를 띄울 수는 없습니다.
- 지난 5개월 동안 이 신뢰 곡선을 올라가서, 지금은 에이전트가 PR 을 자동으로 병합하는 단계에 도달했습니다. 강연 당일 아침에 일어나 보니 PR 약 20개가 이미 병합되어 있었고, Lauren 은 main 브랜치에서 그 PR 들을 사후 검토했는데 문제가 없었다고 합니다.
- 생산성 변화 : 입사 첫 달에는 코드베이스를 익히느라 생산성이 낮았지만, 강연 전달에는 PR 약 1,000개를 병합했고, 강연 당월에는 12일까지 약 800개를 병합했습니다.
  - (2차 자료) The Neuron 등에는 "월 약 2,000개, 8월 2,462개"라는 수치가 실려 있습니다. 강연 이후 집계된 수치로 보입니다.
- 진행자는 이 여정을 다음 순서로 요약했고, Lauren 도 동의했습니다.
  - 검증 스킬 구축 → 로컬에서 신뢰 확보 → 클라우드 에이전트로 확장(버그 보고 등을 스스로 가져가서 PR 생성) → 자동 병합과 main 에서의 사후 검토
- 이 곡선을 건너뛰는 지름길은 없다고 강조합니다. 결국 개인이 에이전트를 얼마나 신뢰하느냐의 문제이기 때문입니다.

### 2. 검증 스킬
- Lauren 은 에이전트를 다룰 때 가장 중요한 스킬로 **검증(verification)** 을 꼽습니다.
- 여기서 검증이란, 사용자가 앱을 쓰는 방식 그대로 에이전트가 코드를 실제로 실행하고, CPU 트레이스나 힙 스냅샷을 찍고, iOS 시뮬레이터를 여는 등의 방법으로 직접 확인하는 능력을 뜻합니다.
- 인용 취지 : 검증은 에이전트가 **좋은** 코드를 쓴다고 보장하지는 않지만, 적어도 **올바른** 코드를 쓰게 해 줍니다. 그리고 이것이 에이전트를 신뢰하는 데 큰 진전입니다.
- 검증 스킬이 없으면 사람이 검증자가 됩니다. 사람이 로컬 빌드를 열고, 스크린샷과 콘솔 에러를 복사해서 에이전트에게 전달하는 병목이 되기 때문에 병렬화할 수 없습니다.
- 계기가 된 일화
  - Lauren 은 입사 첫 주에 출시를 일주일 앞둔 Cursor 의 Agents Window(React 앱)의 성능 작업을 맡았습니다.
  - Chrome DevTools 로 트레이스를 직접 찍고 플레임 그래프를 해석하려 했지만, 코드베이스를 모르는 상태였고 에이전트도 엉뚱한 원인을 자신 있게 지목했습니다.
  - 그래서 처음 만든 스킬이 **control glass** 스킬입니다. Glass 는 Agents Window 의 내부 코드 네임입니다.
- 스킬 코드 자체는 에이전트가 쉽게 만들어 줄 수 있습니다. 웹과 Electron 앱은 Chrome DevTools Protocol(CDP)로, iOS 앱은 Apple 이 제공하는 시뮬레이터 도구로 실행, 트레이스 수집, 프로그래밍 방식의 조작을 에이전트에게 가르치면 됩니다.
- (2차 자료) 검증 절차를 Doctor(환경 점검) → Launch(앱 실행) → Drive(기능 조작) → Evidence(증거 수집) → Cleanup(정리)의 다섯 단계로 정리한 내용은 대본에서는 확인되지 않았습니다.

### 3. 기능 지도 (Feature Map)
- control glass 스킬로 에이전트가 앱을 실행할 수는 있게 되었지만, 에이전트는 앱에 어떤 기능이 어디에 있는지 몰랐습니다. "왼쪽 사이드바가 느리다"는 보고를 받아도 코드를 뒤지고 UI 를 헤매느라 쓸모가 없었습니다.
- 그래서 스킬에 **기능 지도(feature map)** 라는 파일을 함께 두었습니다. 기능마다 다음 내용을 적습니다.
  - 사용자 관점에서 그 기능에 도달하는 방법
  - 관련된 하위 기능과 키보드 단축키
  - CDP 로 요소를 선택할 때 쓰는 DOM 속성
- 내부 Slack 채널에는 스크린샷 한 장에 "???"만 적힌 수준의 낮은 품질의 피드백이 자주 올라옵니다. 기능 지도가 있으면 이렇게 모호한 보고나 스크린샷도 실제 기능과 재현 경로로 연결할 수 있습니다.
- pstack 에는 기능 지도를 포함한 검증 스킬을 만들어 주는 **create verification** 스킬과, 기능 지도를 최신 상태로 유지하는 **maintain verification** 스킬이 들어 있습니다. create verification 스킬은 코드를 탐색해서 초기 기능 지도를 만들어 줍니다.
- (2차 자료) 기능 지도를 "구체화한 기억(제품의 전체 이력이 아니라 지금 있는 것만 적고, 앱이 정본이며 지도는 값싼 색인)"으로 설명하는 내용은 대본에서는 확인되지 않았습니다.

### 4. pstack (Potato Stack)
- 여러 스킬을 묶은 Cursor 플러그인입니다. 공식 소스는 Cursor 의 공개 플러그인 저장소 안에 있는 [pstack 폴더](https://github.com/cursor/plugins/tree/main/pstack)입니다.
- 이름의 유래 : Y Combinator CEO 인 Garry Tan 이 만든 플러그인 gstack(Garry Stack)을 패러디했습니다. 두 사람은 성이 같지만 친척은 아니며, P 는 닉네임 poteto 에서 따왔습니다.
- 처음부터 pstack 을 만들려고 계획한 것은 아닙니다. control glass 스킬, 그 다음에는 how 스킬처럼, 에이전트가 실패하는 모습을 관찰할 때마다 그 실패 유형을 하나씩 스킬로 만들어서 쌓아 나갔습니다.
  - 예를 들어 에이전트가 "원인은 이것"이라고 단정했지만, 도구 호출 기록을 보니 정작 관련 코드를 읽지도 않은 경우가 있었습니다.
- 철학 : 환각하지 말고, 실제로 코드를 검색해서 확인하고, 서브에이전트를 많이 쓰고, 추측을 멈춥니다.
- 매니저 비유 : 코딩은 잘하지만 비즈니스 맥락이 전혀 없는 신입 엔지니어를 효과적으로 일하게 만드는 수단이 스킬입니다. 스킬은 마크다운일 뿐이지만, 품질 높은 토큰을 먼저 주면 에이전트가 더 높은 수준의 패턴을 따르게 됩니다.
- 대본에 언급된 스킬 : control glass, how, create verification, maintain verification, potato mode(그 안의 eval playbook)
- 무작정 신뢰하지 말고, pstack 을 포크해서 자신의 기준에 맞게 고쳐 쓰라고 권합니다. 엔지니어마다 코드베이스에서 중요하게 여기는 기준이 다르기 때문입니다.
- (2차 자료) `/why`, `/recall`, `/teach`, `/architect`, `/arena`, `/swarm`, `/interrogate`, `/tdd`, `/unslop` 등의 스킬 목록, Cursor 팀에서 주 1만 번 사용되었다는 수치, 외부 시험에서 기본 설정보다 시간과 토큰을 두 배 썼지만 환각 오류 3개를 잡았다는 결과는 대본에서는 확인되지 않았습니다.

### 5. Evals
- Lauren 이 생각하는 eval 은 「에이전트를 위한 단위 테스트」입니다. 특별한 프레임워크 없이도, 원하는 엄밀성 수준에 맞춰 직접 만들 수 있습니다.
- pstack 의 potato mode 안에 있는 **eval playbook** 의 방식은 다음과 같습니다.
  - 코디네이터 에이전트가 스킬이 해야 할 일에 대한 채점표(루브릭)를 만듭니다.
  - 서브에이전트를 여러 개 띄우고, 각자 별도 디렉터리에서 작업하게 합니다. 디렉터리 이름은 서브에이전트가 평가받고 있다는 사실을 눈치채지 못하게 짓습니다. 에이전트는 평가 중이라는 것을 알아채면 행동을 바꾸기 때문입니다.
  - Cursor 는 여러 모델을 지원하므로, 같은 스킬을 여러 모델로 평가해서 모델별 성능을 비교할 수 있습니다.
  - 다른 모델을 쓰는 심판 에이전트를 두어, 채점하는 첫 번째 모델이 편향되지 않았는지 교차 확인합니다.
  - 점수를 기준으로 언덕 오르기(hill climbing)를 합니다. 예를 들어 `/loop` 로 "모든 항목이 10점 만점에 10점이 될 때까지 반복하라"고 지시합니다.
- 스킬을 수정할 때마다 eval playbook 을 돌려서 원하는 결과가 나오는지 확인합니다. 검증 스킬 자체도 같은 방식으로 검증하며 다듬었습니다.
- 스킬을 유지보수하려면 안목과 관찰이 필요합니다. 페어 프로그래밍에서 옆자리 동료에게 "왜 이렇게 안 했어?"라고 묻는 사람처럼, 처음에는 에이전트의 도구 호출, 코드, 생각 과정을 직접 읽으면서 어디서 실패하는지 찾고, 그 실패를 스킬로 만듭니다.
- 셰프 비유 : 이제 엔지니어는 요리를 직접 다 하는 사람이 아니라 주방을 설계하고 각 조리 담당에게 일을 나눠 주는 총괄 셰프에 가깝습니다.

### 6. 로컬에서 시작해 클라우드 에이전트로 확장하기
- 검증 스킬은 로컬에서 시작하는 것이 가장 좋습니다. 에이전트가 앱을 띄우고 어떤 API 로 조작하는지 직접 관찰할 수 있기 때문입니다.
- 환경을 한 번 설정해 두면, 검증 스킬은 개인뿐 아니라 팀과 회사 전체에 이득을 줍니다. 클라우드 에이전트와 자동화에서 같은 스킬을 쓸 수 있기 때문입니다.
- 예시 : **Benny**
  - 들어오는 버그 보고를 받아서, 클라우드에 있는 자신의 데스크톱에서 Cursor 를 실행하고, 같은 control 스킬로 앱을 조작해 버그를 재현합니다.
  - 강연에서 보여 준 사례에서는 Benny 가 버그를 재현한 뒤, 그 버그가 main 브랜치에서는 이미 고쳐졌다는 사실까지 확인했습니다. 따라서 남은 일은 새 빌드를 배포하는 것뿐이었습니다.
- 경고 : 아직 에이전트를 하나하나 지켜보는 단계라면, 클라우드 에이전트를 수백, 수천 개 띄우는 단계로 바로 건너뛰지 말아야 합니다. 토큰만 낭비하고 비용이 매우 커집니다.

### 7. 코드베이스 리팩토링과 가드레일
- 업계에서 논쟁이 많은 "앱을 다시 써야 하는가"라는 질문에 대해, Lauren 은 경우에 따라 다시 쓰는 것을 고려할 만하다고 주장합니다.
- 큰 테크 기업의 문제가 이제 모두의 문제가 되었습니다.
  - Meta 처럼 엔지니어가 수만 명인 모노레포에서는 코드 품질이 생각보다 좋지 않습니다. Lauren 은 "AI 슬롭 이전에는 휴먼 슬롭이 있었다"고 농담합니다.
  - 그래서 큰 기업의 인프라는 가장 역량이 낮은 엔지니어를 기준으로 프레임워크, 컨벤션, 가드레일을 갖추고 권한을 제한합니다(인턴이 운영 DB 를 날리지 못하게 하는 식입니다).
- 이런 인프라가 갖춰진 기존 앱(brownfield)에서는 에이전트도 꽤 잘 작업합니다. 반대로 새로 만드는 앱(greenfield)은 가장 큰 위험이자 가장 큰 기회입니다.
- Grokbot 도 처음에는 사람이 코드를 전혀 읽지 않는 바이브 코딩으로 빠르게 만들어졌습니다. 가드레일이 없으면 에이전트는 가장 편한 지름길로 문제를 풀고, 시간이 지나면 아무도 이해하지 못하는 코드베이스가 됩니다. Lauren 은 이것을 "organic architecture"라고 표현했습니다.
- 그래서 처음부터 강한 제약을 두고 코드베이스를 시작해야 합니다. Lauren 은 600개가 넘는 PR 로 Grokbot 전체를 새 아키텍처로 리팩토링했고, 지금은 코드를 거의 보지 않는 단계에 도달했습니다.
- CI 가 매우 귀찮아서 사람이 코드를 쓰기는 힘들지만, 그 귀찮음은 에이전트가 모두 흡수합니다.

### 8. PR 크기
- PR 크기에 상한은 없고, 작업에 따라 50줄에서 1,000줄 정도까지 다양합니다.
- 다만 에이전트에게 작업을 여러 PR 로 나누도록 권합니다.
  - git 이력은 풍부한 맥락이 되므로, PR 하나가 작은 작업 하나를 원자적으로 설명하게 합니다.
  - 되돌리기 쉽고, 버그를 낸 PR 을 찾기 쉽습니다. 4만 줄짜리 PR 안에서는 무엇이 들어갔는지 알 수 없습니다.
- (2차 자료) "코드를 쓰는 주체와 검증하는 주체를 나눈다"는 내용은 PR 크기 문맥에서는 확인되지 않았습니다. 대본에서 가장 가까운 내용은 eval 에서 다른 모델의 심판 에이전트를 두는 방식입니다.

### 9. CI 제약과 Dune 아키텍처
- **Dune** 은 Grokbot 에 적용한 아키텍처의 코드 네임입니다. 「Electron 앱을 위한 Next.js」와 비슷하며, 에이전트가 코드를 쓰는 것을 전제로 설계했습니다. 오픈소스로 공개할 계획은 없고, 아이디어와 원칙의 모음에 가깝다고 합니다.
- CI 는 모든 것을 검사하기 때문에 상당히 귀찮습니다. 예시는 다음과 같습니다.
  - React `useEffect` 사용 금지 : React 에서 가장 큰 함정이기 때문에 사용하면 CI 가 실패합니다.
  - 코드 주석 금지 : 에이전트가 다는 주석은 99% 가 코드와 상관없는 과거 이야기입니다. 예를 들어 PR 하나에 대한 지적을 "Lauren 이 이렇게 하지 말라고 했다"는 영구 규칙처럼 주석으로 남깁니다.
  - Electron main 과 renderer 격리 : Agents Window 는 프로세스 격리가 약해서, 무거운 연산이나 I/O 코드가 렌더러 스레드로 딸려 들어가 성능이 자주 퇴행합니다. 60 FPS 를 유지하려면 프레임마다 16ms 안에 그려야 하므로, 이를 넘기면 화면이 끊깁니다. Grokbot 은 `electron main` 과 `electron renderer` 디렉터리를 나누고, CI 에서 의존 그래프를 검사해서 서로의 코드를 import 하지 못하게 막습니다.
- 강제 수준을 여러 겹으로 쌓습니다.
  - **코드베이스 구조 (가장 강함)** : 에이전트는 기존 패턴을 복사하는 것을 좋아하므로, 엄격하고 관례적인 구조 자체가 가장 강한 강제 수단입니다. Grokbot 에는 feature, entry point, transcript card 같은 개념이 있고, 하나의 feature 에 속한 코드는 한 디렉터리에 모여 있어서 작업의 약 80% 는 그 디렉터리 안에서 끝납니다. 핵심 원칙은 「가장 짧은 길이 가장 좋은 길」입니다. 에이전트는 어차피 지름길을 택하므로, 지름길이 곧 올바른 길이 되도록 설계합니다.
  - **정적 분석 (강함)** : CI 검사, 관찰한 나쁜 패턴에 대한 린트, 컴파일러 진단은 CI 를 실패시키는 강한 제약입니다.
  - **규칙, 스킬, BugBot (약함)** : 에이전트가 잊어버리거나 일관되게 적용하지 않을 수 있습니다. 함께 쓰되 유일한 강제 수단으로 삼으면, 코드베이스가 망가지는 것은 시간문제입니다.
- 기술 스택 선택도 중요합니다. 예를 들어 Rust 는 컴파일러가 많은 것을 강제하므로, unsafe 블록만 막으면 컴파일되는 코드는 대체로 동작한다고 믿을 수 있습니다.
- 가장 나쁜 상태는 코드베이스의 불변 조건을 사람이 코드 리뷰로 일일이 지적해서 지키는 것입니다. 리뷰에서 "이렇게 하지 마세요"라고 써야 할 때마다 코드 스멜로 여기고, 린트 규칙이나 CI 실패로 바꾸거나 그 문제가 아예 생기지 않도록 구조를 바꿀 방법을 찾아야 합니다.

### 10. 토큰 사용량, ROI, 비용
- Lauren 은 토큰을 무제한으로 쓰는 AI 회사에 다니므로, 모두가 똑같이 할 수는 없다고 인정합니다. 다만 큰돈을 쓰지 않고도 이 단계에 도달할 수 있다고 봅니다.
- 엔지니어링 리더에게는 ROI 의 문제입니다.
  - 코드베이스 리팩토링과 제약 추가에는 초기에 토큰이 많이 듭니다.
  - 하지만 혼자서는 몇 년이 걸렸을 프레임워크 구축, 리팩토링, 검증을 에이전트 덕분에 해냈습니다. 사람을 더 고용할지, 가장 단순한 에이전트도 잘 일할 수 있는 코드베이스를 만드는 데 토큰을 쓸지의 트레이드오프입니다.
  - 그렇게 만든 코드베이스에서는 가장 큰 모델이 아니어도 훌륭하게 코드를 씁니다. 또한 PM, 디자이너, Grokbot 에 익숙하지 않은 엔지니어도 지속 가능한 방식으로 기여할 수 있게 됩니다.
- 강연 당일 Grok 4.6 이 발표되었습니다. Lauren 은 토큰당 비용이 4.5 와 같다고 알고 있다고 조심스럽게 언급했습니다. Cursor 와 SpaceX AI 는 가장 큰 모델이 아니라 비용 대비 지능의 파레토 최적점을 찾는 데 집중한다고 설명했습니다.

### 11. Grokbot 으로 제품팀이 직접 배포하기
- Grokbot 은 강연 전날 출시된 앱으로, 각자 정체성을 가진 에이전트를 만들고 오케스트레이션할 수 있습니다.
- 기존의 Cursor 제품(Agents Window, CLI, IDE)은 개발자 중심 도구였기 때문에, GTM 이나 제품 직군에게는 편한 경험이 아니었습니다. Grokbot 은 iMessage 처럼 익숙한 화면이어서, Lauren 은 이를 기술 직군이 아닌 사람들의 「Cursor 모먼트」라고 표현했습니다.
- 사용 예 : 관리하는 계정마다 에이전트를 하나씩 두거나, PM 이 "Lauren 이 어젯밤 한 일을 요약해 줘"라고 시키는 식입니다.
- PM 도 직접 코드를 배포합니다. PM 이 "이 버그를 고쳤으니 봐 달라"고 하면 Lauren 이 리뷰하는데, 대부분 그대로 승인할 만큼 결과가 좋습니다. Lauren 은 이것을 Dune 아키텍처의 엄격한 제약 덕분에 엔지니어링 전문가가 아닌 사람도 높은 수준으로 기여할 수 있다는 증거로 봅니다.

### 기타
- 진행자 Colin 은 자신을 포함한 청중 대부분이 아직 로컬에서 에이전트 2~3개를 병렬로 돌리는 단계일 것이라고 말했습니다.
- Grokbot 과 Cursor 의 가상화(virtualization)에는 pretext 라는 라이브러리를 사용한다고 잠깐 언급했습니다.

## 핵심 교훈
- 검증 스킬을 만듭니다. 검증은 좋은 코드가 아니라 올바른 코드를 보장하고, 이것이 신뢰의 출발점입니다.
- 기능 지도를 두어서 에이전트가 기능에 도달하는 방법을 알게 합니다.
- 스킬을 evals 로 검증하고, 점수를 기준으로 개선합니다.
- 로컬에서 관찰하며 신뢰를 쌓은 뒤에 클라우드로 넓힙니다.
- 리뷰에서 반복해서 지적하는 내용은 린트와 CI 같은 강한 제약으로 바꿉니다.
- 에이전트가 택하는 지름길이 올바른 길이 되도록 아키텍처 경계를 강제합니다.

## 참고 : 에이전트 게임 스튜디오에 적용할 거리
> agent-game-studio 레포의 세션이 CEO 에게 제출한 분석을 참고용으로 함께 남깁니다.

### 이미 갖춘 것
- QA 리그, 테스트 봇, 프레임 모음표
- 쓰기 훅, 커밋 주인 검사, 코드 자동 검사
- 리뷰어와 QA 분리 (코드를 쓰는 주체 ≠ 검증하는 주체)
- 기간 산정 실측값과 비용 회고

### 빈틈과 적용안 (추천 순서)
1. 게임의 기능 지도를 작성합니다. (기능마다 도달 방법, 조작 방법, 함정)
2. 어댑터마다 게임 검증 스킬(점검 → 실행 → 조작 → 증거 → 정리)을 만들고, 화면에 보이는 변경의 완료 보고에는 증거를 요구합니다.
3. 되풀이되는 반려 사유를 자동 검사(강한 가드)로 바꾸는 경로를 마련합니다.
4. 역할 파일과 스킬을 평가(evals)합니다. 과거에 발생한 사고를 평가 장면으로 사용합니다.
5. 부서와 일감 종류별로 신뢰 단계를 두고, 반려율과 되돌림 횟수에 따라 단계를 올리거나 내립니다.
- 클라우드 에이전트 도입은 보류합니다.

### 대시보드 후보
- **신뢰 판** : 반려율, 되돌림 횟수
- **증거 판** : 그날 병합한 결과물의 캡처
- **검증 범위 판** : 기능 지도 가운데 검증이 닿는 기능의 비율
