# TIL 문서화

전달받은 자료(강연·영상·글 요약, 다른 세션이 보낸 정리, 링크)를 이 저장소의 관례대로 `writing/` 아래 문서로 정리하고, 사용자가 요청하면 커밋하고 푸시합니다.

## 1. 관례 확인

- 짧은 글은 `writing/<주제>/<YYYY-MM-DD> - <제목>.md` 형식으로 둡니다. 날짜는 작성일이고, 주제 폴더(`JPA`, `Kotlin`, `AI` 등)가 없으면 새로 만듭니다.
- `writing/` 문서는 `README.md` 목록에 올리지 않습니다. 사용자가 요청할 때만 추가합니다.
- 작성하기 전에 `ls writing/*`로 기존 주제 폴더를 확인해서, 맞는 폴더가 이미 있으면 그 폴더를 사용합니다.

## 2. 문서 구성

다음 순서를 기본으로 하고, 자료에 없는 섹션은 생략합니다.

1. `# <제목>` 과 한 줄 소개
2. `## 출처`: 원본(영상·글) 링크, 소개 페이지, 발표자·저자 정보
   - 영상을 직접 보지 않고 2차 자료로 정리했다면, 그 사실과 "세부 표현은 원본과 다를 수 있다"는 경고를 인용 블록으로 남기고 2차 자료 링크를 함께 적습니다.
3. `## 챕터` (영상이라면 시각과 챕터를 표로 작성)
4. `## 핵심 내용`: 번호가 붙은 `###` 소제목과 목록
5. `## 핵심 교훈`
6. `## 참고 : ...`: 자료를 보낸 쪽의 적용 분석처럼 부가 내용이 있으면, 출처를 밝히고 참고용으로 남깁니다.
7. `## 참고 링크`: **문서에 나온 모든 링크**를 `| 구분 | 설명 | 링크 |` 표로 모으고, URL 전체를 그대로 보이게 적습니다. 구분 값은 `원본 영상`, `강연 소개`, `관련 저장소`, `2차 자료` 등을 사용합니다.

## 3. 링크 규칙

- 받은 자료에 있는 링크는 하나도 빠뜨리지 않습니다. 본문에서 링크 텍스트 뒤에 가려진 링크도 `참고 링크` 표에 다시 적습니다.
- 받은 자료에 없는 링크(예: 본문에서 언급된 도구의 저장소)는 임의로 추가하지 않습니다. 필요해 보이면 사용자에게 먼저 묻습니다.
- 사용자가 추가를 허용하면 웹 검색으로 찾고, `gh api` 나 WebFetch 로 링크가 실제로 존재하는지 확인한 뒤 넣습니다.
- 공식 소스와 비공식 포트·미러를 구분해서 설명란에 밝힙니다.

## 4. 작성 규칙

- 한국어 본문은 완결된 문장으로 쓰고, 고유 명사와 기술 용어는 원어를 유지합니다.
- 받은 자료의 수치·인용·고유 명사는 바꾸지 않고, 확인되지 않은 내용을 덧붙이지 않습니다.

## 5. 커밋과 푸시

사용자가 요청한 경우에만 수행합니다.

- 해당 문서 파일만 `git add` 합니다. 작업과 무관한 미추적 파일은 포함하지 않습니다.
- 커밋 메시지는 최근 관례를 따릅니다. 예: `docs(writing): add notes on <제목 요약>`
- `main` 에 직접 푸시해 온 저장소이므로, 사용자가 푸시를 요청하면 `git push origin main` 을 실행합니다.
